# TurnBase

## Краткое описание

Это ядро библиотеки для реализации пошаговых многопользовательских игр. В этой папке находятся абстракции игрового поля, игроков, правил, событий, ротации ходов, механики игры и вспомогательные обёртки для защиты от сбоев, таймаутов и удалённых игроков.

## Жизненный цикл игры

Общий цикл координирует `Game<...>`, а содержание моделей, обработку ходов, критерий окончания и вычисление победителей предоставляет реализация `IGameRules`.

### 1. Создание игры

Для создания игры в класс `Game<...>` необходимо передать правила генерируют `IGameRules<...>`. Движок хранит его и использует передаваемые правила для всех последующих операций. 

Во время эого процесса:
- создается поле через `GenerateGameField()`.

### 2. Добавление игроков

Каждый игрок добавляется в `Game` через `AddPlayer`. Во время этого процесса:
- проверяется лимит по числу игроков;
- проверяется, что игра ещё не началась;
- создаётся обёртка `PlayerFailProtection` для безопасности выполнения.

При вызове `Play` движок добавляет недостающих игроков `PlayerLoose`, если зарегистрированных игроков меньше минимума, установленного правилами.

### 3. Начало игры

Перед инициализацией игрокам и логгерам отправляется `GameStarted()`.

### 4. Инициализация игроков

Для каждого игрока в порядке, определяемом `GetInitRotator()` запускается `Init`:
- правила формируют индивидуальный запрос игроку через `GetInitModelForPlayer(...)`;
- игрок получает `InitModel` с `PlayerId`, шириной/высотой поля, набором доступных фигур и лимитом ходов;
- созданное и заполненное поле возвращается в `InitResponseModel`.
- правила проверяют и применяют ответ через `TryApplyInitResponse(...)`.
- `TryApplyInitResponse(...)` в правилах проверяет::
  - корректность размеров;
  - корректность набора фигур;
  - совпадение с допустимым набором для этого игрока.
- Если всё корректно, фигуры раскладываются по основному полю в позиции игрока.
- После успешной инициализации игрока отправляется `GamePlayerInit(...)`
- После успешной инициализации всех игроков отправлятся `GamePlayersInitialized()`


### 5. Ход игрока

Перед каждым ходом игроков проверяется `IsGameOver(...)`. Если условие уже выполнено, ходовая фаза пропускается или завершается без запуска очередной группы.

На каждом ходу для конкретного игрока в порядке, определенном  `GetMoveRotator()` запускается `Move`:

- правила формируют индивидуальный запрос игроку через `GetMoveModelForPlayer(...)`;
- запрашивает автоматический ход через `AutoMove(...)`. если автоматического ответа нет, обращается к игроку через `MakeTurn(...)`.
- игрок получает `KaNoBuMakeTurnModel` с описанием видимого поля;
- игрок создаёт `KaNoBuMoveResponseModel` с одним или несколькими `MoveStep`;
- вызывается `IsMoveValid(...)`;
- если ход валиден, выполняется `TryApplyMoveResponse(...)` Невалидный ответ запрашивается повторно; если игрок не возвращает ответ, игрок считается отключившимся. Правила определяют смысл автоматического ответа и то, когда он заменяет запрос хода у игрока. Проверка и эффекты отдельных шагов, изменение состояния поля и формирование результата хода относятся к реализации правил игры. Движок не интерпретирует содержимое хода.



### 7. Уведомления и логирование

После применения хода происходит:
- вызов `GamePlayerTurn(playerNumber, notification)` у всех игроков и логгеров;
- Правила формируют адресованные игрокам версии уведомления; полная версия передаётся логгерам. 
- Неуспешное действие также приводит к событию `GamePlayerDisconnected(...)`.

### 8. Проверка конца хода и игры

После каждой группы действий ротатор выбирает следующую группу. Если он сообщает, что начался новый раунд, движок вызывает `TurnCompleted(...)` и отправляет `GameTurnFinished()`.

`IsGameOver(...)` проверяется перед следующей группой, а не между игроками внутри уже выбранной группы. Поэтому группа может завершить действия всех своих игроков до следующей проверки. Условие окончания отвечает только на вопрос, продолжать ли игру; оно не определяет список победителей.

### 9. Определение победителей и завершение

Когда `IsGameOver(...)` возвращает `true`, новые группы действий не запускаются. 
Затем движок запрашивает у правил `FindWinners(...)` и передаёт результат через `GameFinished(...)` игрокам и логгерам. Список может содержать ноль, одного или нескольких победителей. 

Таким образом, `IsGameOver(...)` определяет момент остановки, а `FindWinners(...)` отдельно формирует итоговый результат.

## Удалённое подключение

`RemoteGame` подключается к удалённому игроку через сервер. Если при подключении передан `gameId`, сервер ищет свободное место только в игре с этим идентификатором. Если `gameId` не указан или пустой, сервер автоматически подключает клиента к любой игре, в которой есть доступный для подключения удалённый игрок. Если подходящих игр нет, подключение завершается ошибкой.

## Какого типа классы и файлы она должна содержать

Эта папка должна содержать:
- базовые интерфейсы и модели для игрового процесса;
- абстракции поля и фигур (`IField`, `IFigure`);
- интерфейс правил игры (`IGameRules`);
- игровой цикл (`Game`), с инициализацией, ходами, логами и завершением игры;
- протоколы событий для слушателей (`IGameEventListener`);
- ротацию очередности ходов игроков;
- обёртки игроков (`PlayerLoose`, `DelayedPlayer`, `TimeoutPlayer`, `ServerPlayer`, `PlayerFailProtection`);
- сетевые/реплейные варианты игры (`RemoteGame`, `ReplayGame`);
- базовые структуры данных, такие как `Point`, `TaskExtensions` и вспомогательные модели общения.

Данная папка — это общий движок, от которого зависят конкретные игровые реализации, например KaNoBu.

## Роль и устройство

`TurnBase` — это не игровая логика KaNoBu, а обобщённый фреймворк для пошаговых игр. Она задаёт базовый контракт между игроками, правилами, игровым циклом и событиями.

Главные идеи фреймворка:
- игроки реализуют интерфейс `IPlayer<TInitModel,...>` и подписываются на события через `IGameEventListener<TMoveNotificationModel>`;
- правила игры реализуют `IGameRules<TInitModel,...>` и отвечают за генерацию поля, инициализацию, проверку ходов и применение ходов;
- класс `Game<TInitModel,...>` координирует игровой процесс: приглашение игроков, инициализация, выполнение ходов, логирование и завершение;
- `IField` описывает контракт игрового поля, а конкретная реализация (`Field2D`) даёт двумерную сетку для шахматных/пошаговых игр;
- `PlayerRotators` определяют порядок ходов и возможность перехода между раундами;
- `RemoteGame` и `ReplayGame` дают инструменты для удалённой игры и повторного воспроизведения партий.

Слой `TurnBase` должен быть максимально универсальным. Он не должен содержать зависимости на конкретную игру, кроме очень общих типов и интерфейсов. Игра KaNoBu должна расширять этот слой через специализированные модели, фигуры и правила, а не менять ядро движка без необходимости.

Если в проект добавляется новая игра, новый тип игрока, новый формат сетевой коммуникации или новая ротация ходов, изменения в общий движок вносятся только тогда, когда они действительно универсальны. Конкретная игровая логика должна находиться внутри `TurnBase.KaNoBu`, а не в ядре `TurnBase`; это также определяет правильное место для будущих изменений.
